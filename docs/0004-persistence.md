## Conventions

Taken from **`0x99M/videos-recipes`**, the most recent build and the closest in shape to this one.
Established there and followed here: Drizzle over `drizzle-orm/node-postgres` with a `pg` Pool (not
the `postgres` driver); `src/db/{schema,pool,migrate}.ts`; migrations generated by drizzle-kit into
`drizzle/` and applied in production by the **compiled** `dist/db/migrate.js`, so drizzle-kit stays
a devDependency and never enters the runtime image; a Railway `preDeployCommand` running it;
snake_case columns with camelCase properties; named `{table}_{col}_idx` / `_unique` /
`{col}_positive` constraints; table config as `(table) => [...]`; no `pgEnum`, no `relations()`; and
a comment above every column saying *why*.

Three deliberate divergences, each because this is a money system rather than a content one.

**The schema lives in `packages/persistence`, not in an app.** Each platform deploys as its own
service with its own Postgres — they share code, not infrastructure — so one schema is applied
separately per deployment. Nothing in it is keyed by platform, because every row in a given database
belongs to the same one.

**Timestamps are `timestamptz`.** The canonical `Instant` is UTC-only by construction and the column
should say so; a bare `timestamp` compares and casts against whatever the session's TimeZone happens
to be, which is a silent hazard in an audit trail over money.

**A numeric column is never read with `Number()`.** More on that below.

## Money: two decimal digits, and still exact

Money is `numeric(14, 2)` — the two decimal digits you asked for. That is not in tension with the
domain's integer halalas, because `numeric` is exact decimal and the `pg` driver returns it as a
**string** precisely so nothing is lost on the way out. The column keeps the table readable to
anyone querying by hand; the integer keeps the arithmetic exact in the engine.

What would break it is the ordinary way to read a numeric column:

```ts
Number(row.total)        // ✗ a float, and the whole codebase exists to avoid one
parseFloat(row.total)    // ✗ parseFloat('1.005') * 100 === 100.49999999999999
numericToMinor(row.total) // ✓ digit-wise, through the same checked constructor adapters use
```

`src/db/money.ts` is the only place the two representations meet. Precision 14 is chosen so
`MAX_MINOR` fits exactly: SAR 9,007,199,254.74.

**One live constraint, stated rather than papered over.** Scale 2 cannot represent the three-decimal
currencies `CURRENCY_CODES` still lists (KWD, BHD). `assertStorableCurrency` rejects them instead of
silently dropping a digit; supporting them means a migration to scale 3, not a cast.

## The database enforces the domain

Every `text` column that holds a domain enum has a CHECK constraint built from the **same frozen
const tuple** in `@ghalla/contracts` that `z.enum()` and every adapter lookup table use — one list,
not four. Beyond those, the constraints carry rules the engine also asserts, so a bad row cannot be
written even by something that bypasses the engine:

- a line total that is not gross minus its discount
- a reversal whose parts do not sum to its stated total
- a fee rule whose floor is above its cap, or whose percentage is negative
- a profit row claiming more goods came back than went out
- a computed profit row with no margin, or a rejected one carrying totals
- a referrer with a path in it — PII that slipped past the adapter
- a card payment with no scheme, or a non-card payment with one

That last group is the reason these tests run against a real database rather than a mock: a CHECK
constraint that does not compile, or does not fire, is worse than no constraint, because the comment
beside it says it does. **PGlite** — Postgres compiled to WebAssembly — applies the actual migration
in-process, so there is no Docker dependency and no service container in CI.

It caught a real bug immediately. `UNIQUE (fee_rule_set_id, instrument, scheme, provider)` does not
prevent duplicates when `provider` is NULL, because SQL treats every NULL as distinct — and unset is
the *ordinary* case for these columns, so the constraint was guarding only the rules least likely to
be duplicated. Fixed with `NULLS NOT DISTINCT`, which is what makes "two rules with one key would
mean row order decides the fee" actually unrepresentable.

## The two non-negotiables

**Costs are snapshotted, never joined live.** `cost_history` is slowly-changing-dimension type 2 on
a half-open `[effectiveFrom, effectiveTo)` window, keyed on the product key rather than the SKU. A
correction closes the open row and opens a new one; it never updates in place. `resolveAsOf` is one
indexed predicate, and there is a test proving an order placed in March still reads the March cost
after the merchant changes it in June.

**Rollups are incremental.** Writing an `order_profit` row marks the affected `(store, business
date)` buckets dirty in the *same transaction* — a result stored without its buckets marked is a
rollup that is silently stale, and since the sweep only looks at dirty rows, nothing would ever
notice. The business date is denormalized onto the profit row so a carrier cost that lands days late
dirties **the order's** bucket, not today's. There is a test for that too.

## One pnpm note worth keeping

drizzle-kit reaches for drizzle-orm at runtime but declares no dependency on it — it relies on a
hoisted `node_modules`. Under this repo's `hoist: false` the ESM resolver walks up from drizzle-kit's
*real* path inside the store, where drizzle-orm is not, and the CLI exits with "Please install latest
version of drizzle-orm" while the correct version sits one directory away.

The fix is a **private** hoist of that one package: `hoistPattern: ['drizzle-orm']` puts it in
`node_modules/.pnpm/node_modules`, on the resolution path for packages inside the store and not for
ours. Public-hoisting it would also have worked and would have quietly made the ORM resolvable from
`packages/core` — the one thing the isolated layout exists to prevent. Verified after the change:
`packages/core` still cannot resolve `drizzle-orm` at runtime or at typecheck.

## What is not built yet

Repositories for orders, shipments, reversals and the catalogue; the rollup rebuild worker; the
webhook-event writer. The schema and the migration cover them — only the query code is missing.
Next after that is `packages/ingestion` against a fake in-memory adapter, which is where the queue
rules from the brief (never process inline, one rate-limited queue per store, every job replayable)
get built and tested without touching a real platform.
